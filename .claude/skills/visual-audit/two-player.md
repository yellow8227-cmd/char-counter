# 두 사람이 실제로 만나는지 검사 (온라인 대전)

`jelly-shooting/tools/two-player-test.html`

## 실행

```bash
node <러너>.mjs   # 크로미움을 --allow-file-access-from-files 로 띄우고 이 파일을 연다
```

파일을 브라우저에서 그냥 열어도 된다(같은 폴더의 `../index.html`을 iframe으로 두 개 띄운다).
`--allow-file-access-from-files` 없이 file:// 로 열면 iframe 내부에 접근할 수 없어 검사가 멈춘다.

## 무엇을 하는가

같은 게임을 iframe 두 개로 띄우고, 두 인스턴스에 **broadcast·presence를 공유하는 가짜
supabase 클라이언트**를 꽂는다. 그러면 서버 없이도 "둘이 서로를 보는가"를 검사할 수 있다.

| 검사 | 왜 |
| --- | --- |
| 방 만들기 → 코드로 입장 | 기본 경로 |
| 손님이 먼저 들어오는 순서 | 양쪽 다 인사하므로 원래 되지만, 회귀 방지 |
| 공개 방 목록에 방이 뜨는가 | **로비에 붙은 뒤 만든 방이 등록되는지** |
| 목록에서 눌러 입장 | 목록 → 입장 배선 |
| 랜덤 매칭이 열린 방으로 가는가 | 새 방을 열면 둘 다 방만 만들고 안 만난다 |
| 첫 인사가 유실돼도 만나는가 | 모바일에서 흔하다. `BUS.drop`으로 재현 |
| 코드 해석 | 소문자·공백·하이픈·링크 붙여넣기 |
| 나가면 상대가 아는가 | bye 전달 |

## 반드시 알아야 할 함정

**게임의 최상위 `let`/`const`는 window 속성이 아니다.** `frame.contentWindow.net`은
undefined다. 프레임 안에서 `contentWindow.eval('net.room')`으로 읽어야 전역 렉시컬
환경이 보인다.

**about:blank도 `readyState==='complete'`다.** iframe의 load 이벤트나 readyState로
준비를 판단하면 빈 문서를 실제 페이지로 착각한다. 게임 함수(`saveNick` 등)가 실제로
올라올 때까지 기다려야 한다.

**호출 순서를 실제 사용과 같게 두어야 한다.** 화면을 열자마자 방을 만들면 로비 구독
콜백이 방 코드가 정해진 뒤에 실행되어 등록이 우연히 성공한다. 실제 사용자는 화면을
열고 몇 초 뒤에 누르므로, 검사도 `await sleep(700)`을 넣어야 버그가 드러난다.
이걸 몰라서 처음엔 고치기 전 코드도 통과했다.

## 이 검사로 실제로 잡은 것

- 로비에 붙은 뒤 만든 방이 **한 번도 등록되지 않았다**. `netEnterRoom`이 맨 처음
  `netLeave()`를 부르고 그 안에서 `hubUnadvertise()`가 돌았는데, 그 뒤 `hubJoin()`은
  이미 붙어 있으면 그냥 true만 돌려주고 등록을 안 했다. 그래서 '지금 열린 방'이 늘 비고
  랜덤 매칭은 매번 새 방을 열었다(→ 둘 다 방만 만들고 못 만남)
- 인사(hello)를 구독 직후 한 번만 보내서, 그 한 통이 유실되면 둘 다 영원히 대기했다

## 한계

가짜 서버라서 **서버 설정 문제는 알 수 없다**. Supabase Realtime이 꺼져 있거나 키가
틀린 경우는 배포된 https 주소에서 두 기기로 확인해야 한다.
