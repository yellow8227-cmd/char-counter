# 화면 시각 검사

눈으로 스크린샷을 보는 것만으로는 시각 버그를 놓친다. 이 도구는 **실제 폰 뷰포트**에서
화면을 하나씩 펼쳐 보며 기계적으로 검사한다.

## 실행

```bash
node jelly-shooting/tools/visual-audit.mjs jelly-shooting/index.html 360,390,430
```

스크린샷까지 받으려면:

```bash
node jelly-shooting/tools/visual-audit.mjs jelly-shooting/index.html 360,430 --shot /tmp/shots
```

문제가 있으면 종료 코드 1, 없으면 0. 인자 없이 실행하면 `index.html`, `360,390,430`이 기본값.
크로미움을 못 찾으면 `CHROME_PATH=/path/to/chrome` 으로 지정한다.

## 무엇을 잡는가

| 검사 | 왜 |
| --- | --- |
| **넘침** | 요소가 화면 좌우로 삐져나가 잘린다 |
| **겹침** | 떠 있는(absolute/fixed) 요소끼리 겹쳐 뒤에 있는 쪽 글자가 안 보인다 |
| **글자 잘림** | `white-space:nowrap` 인 곳의 글자가 상자보다 길다 |
| **작은 버튼** | 34px 미만은 손가락으로 정확히 누르기 어렵다 |
| **CSS 클래스 충돌** | 한 요소에 함께 쓴 두 클래스가 같은 속성을 다투면 뒤에 선언된 쪽이 이긴다 |
| **세로 잘림** | `overflow-y:hidden` 인데 내용이 화면보다 길다 |
| **페이지 가로 스크롤** | 본문이 가로로 밀린다 |

`!important` 로 이기는 선언은 일부러 그런 것이므로 충돌로 세지 않는다(`.hide` 등).

## 반드시 알아야 할 함정

**헤드리스 크로미움은 창을 500px 미만으로 줄이지 못한다.**
`--window-size=360,820` 을 줘도 `innerWidth` 는 500 이고 스크린샷만 360으로 잘린다.
그래서 스크린샷 오른쪽이 잘려 보이는 것을 "레이아웃 버그"로 오진하기 쉽다.

CSS로 폭을 덮어쓰는 우회도 **틀린다** — `vw` 단위와 `clamp()` 가 여전히 실제 뷰포트(500px)를
따라가므로 카드 폭이 다 어긋나고 검사 결과가 통째로 거짓이 된다.

이 도구는 CDP `Emulation.setDeviceMetricsOverride` 로 **진짜 뷰포트**를 바꾼다.
그게 이 도구가 존재하는 이유다. 의존성은 없다(node 내장 WebSocket + 로컬 크로미움).

## 새 페이지에 붙이기

화면이 여러 개인 앱(한 번에 하나만 보이는 구조)은 페이지에 훅을 하나 둔다.
숨은 요소는 크기가 0이라 검사할 수 없으므로, 페이지가 하나씩 펼쳐 주면서 검사 함수를 불러야 한다.

```js
// 검사 도구가 부를 때만 실행되므로 앱 동작에는 영향이 없다
window.__auditEach = function(scan){
  SCREENS.forEach(name => {
    showScreen(name);          // 그 화면을 펼친다
    prepare[name]?.();         // 목록·표 같은 동적 내용을 채운다
    scan(name, $(name));       // 검사
  });
};
```

훅이 없으면 현재 보이는 화면만 검사한다.

**검사가 의미 있으려면 화면에 실제 내용이 들어 있어야 한다.** 빈 목록·빈 표는 넘치지 않는다.
훅 안에서 닉네임·코인·아이템 같은 값을 채워 두고 목록을 만들어 준 뒤 검사한다.

## 고친 뒤

수정 후 다시 돌려 `전부 통과` 를 확인한다. 이 도구로 실제로 잡았던 것들:

- 범례 칩 클래스 이름이 `.lg` 라서 `<button class="btn lg">` 의 배경·글자색·정렬까지 덮었다.
  큰 버튼 네 개가 분홍 그라데이션을 잃고 흰 카드로 보였다
- 입력칸 스타일을 id 목록으로 지정해서, 나중에 추가한 입력칸 다섯 개가 전부 빠졌다.
  그 칸들만 브라우저 기본 모양(높이 18px)이었다
- 속도 버튼 24px, 새로고침 칩 26px — 손가락으로 누르기 어려웠다
- 게임 HUD가 94% 폭이라 코인 칩이 음향 버튼 뒤로, 목숨 칩이 상대 정보 바 뒤로 숨었다.
  세 요소 다 제자리에 얌전히 있어서 넘침 검사로는 안 잡혔다 — 겹침 검사가 필요한 이유다

**겹침 검사가 보는 것**: 떠 있는(absolute/fixed) 요소 **와 그 안에 담긴 내용**이 대상이다.
화면을 통째로 덮는 것(화면 전환 레이어·카운트다운)은 의도된 것이므로 뺀다 — 그 안의 본문끼리는
정상 배치이므로 세지 않는다. 글자나 조작 요소가 없는 장식(블롭)도 뺀다. 부모-자식은 당연히
겹치므로 뺀다. 남은 쌍이 6px 넘게 겹치면 알린다.

'안에 담긴 내용'까지 보는 이유: HUD를 absolute 컨테이너 안에 넣어 static으로 바꾸자,
자기 좌표는 그대로인데 검사 대상에서 빠져 오른쪽 위 버튼이 그 위를 덮어도 조용히 통과했다.
absolute인 것끼리만 비교하면 이 구멍이 생긴다.

**겹침을 상수로 피하지 마라.** 상대 정보 바를 `top:82px`로 두고 HUD 두 줄 아래라고 계산해
두었는데, 칩 padding이 2px 늘어 세 줄이 되자 다시 겹쳤다. 세로로 쌓이는 것들은 같은
flex 컨테이너에 넣어 구조적으로 겹칠 수 없게 만드는 편이 낫다.

## 아이폰 안전영역은 따로 검사한다

```bash
node jelly-shooting/tools/safe-area-audit.mjs
```

`viewport-fit=cover` + `apple-mobile-web-app-status-bar-style: black-translucent` 이면
화면이 **상태바(시계·배터리) 아래까지 늘어난다.** 그 자리에 버튼을 두면 눌러도 iOS가
터치를 먼저 먹어 **"안 눌리는 버튼"** 이 된다. 스크린샷에는 멀쩡히 보이고, 넘침·겹침
검사도 통과한다 — 좌표상 화면 안이니까.

**헤드리스 크로미움은 `env(safe-area-inset-*)`를 항상 0으로 준다.** 그래서 이 도구는
`--sat/--sab` 토큰을 실제 아이폰 값(위 47px · 아래 34px)으로 덮어쓰고, 화면마다
'누를 수 있는 것'이 그 띠에 걸치는지 본다. env() 를 직접 쓰지 말고 토큰을 한 번 정의해
두면(`:root{--sat:env(safe-area-inset-top,0px)}`) 이렇게 시험할 수 있다.

**스크롤되는 화면은 '가장 불리한 스크롤 위치'에서 봐야 한다.** 맨 위로 올린 상태에서
위 띠에 걸리면 영원히 못 누르고, 맨 아래로 내린 상태에서 아래 띠에 걸리면 그것도 못
누른다. 그 반대는 스크롤로 꺼낼 수 있으니 문제가 아니다. 이걸 구분하지 않으면
'스크롤하면 되는 것'까지 오류로 잡혀 진짜 문제가 묻힌다.

이 도구로 실제로 잡은 것: 판을 3단으로 바꾸면서 위 띠가 화면 맨 위로 올라가자
⏸️ · 🔊 · 🎵 와 던지는 사람의 🏠 가 전부 상태바 아래로 들어가 **눌리지 않았다**
(고치기 전 23건 → 0건).

## 온라인 대전은 따로 검사한다

화면 검사로는 "둘이 서로를 보는가"를 알 수 없다. 그건 `two-player.md` 를 보라 —
같은 게임을 iframe 두 개(여러 명 대전은 네 개)로 띄우고 broadcast·presence를 공유하는
가짜 서버를 꽂아 방 등록 누락·인사 유실·랜덤 매칭 타이밍·정원 초과·탈락 순위를 잡는다.

**여러 명이 되면 HUD 높이를 재라.** 상대 정보 칩을 한 줄에 하나씩 놓으면 세 명만 되어도
상자가 네 줄(130px)이 되어 젤리 떨어지는 길목을 가린다. 눈으로는 "잘 나오네" 싶고
넘침·겹침 검사도 통과한다. 칩 폭과 상자 안쪽 폭을 실제로 찍어 보고, 안 들어가면
글자를 줄여라(점수 네 자리 → 목숨 숫자 + 선두 👑).

## 캔버스로 그린 것은 화소로 재라 (악세서리에서 배운 것)

시각 검사 도구는 **DOM** 을 본다. 캔버스 안에 그린 것(캐릭터·악세서리)은 넘침도 겹침도
안 잡힌다. 눈으로는 "대충 위에 있네" 하고 넘어가므로 스모크 검사에서 화소로 재야 한다.
자세한 규칙과 함정은 `jelly-shooting/docs/악세서리.md` 에 있고, 검사 만들 때 쓸 것만 옮긴다.

**알파 차이로 물건을 찾으면 안 된다.** 이미 불투명한 데(강아지 귀) 위에 놓이는 물건은
알파가 하나도 안 늘어나 "안 그려짐"으로 나온다. 흰 바닥을 깔아 전부 불투명하게 만든 뒤
**색이 크게 달라진 곳**을 물건으로 본다 — 그러면 빛무리·그늘도 문턱으로 걸러진다.

**'가장 위 화소'를 기준선으로 쓰면 안 된다.** 가느다란 조각(뒷머리·애교머리)이 훨씬 위까지
뻗어 있으면 실제로는 떠 있는 물건도 '닿았다'고 나온다. 가운데값을 쓰거나, '가운데를 지나는
이어진 폭'처럼 두께를 요구하는 기준으로 잡아라.

**반투명한 것을 검사할 때 위치 편향을 조심하라.** 렌즈 전체를 뭉쳐 평균 내면 위아래
그라데이션의 밝기 차를 "속이 비친다"로 잘못 읽는다 — 불투명하게 만들어도 통과했다.
같은 줄끼리 비교하고, **문턱은 반대 극단을 실제로 만들어 재서** 정하라(불투명 렌즈도
광택 때문에 12는 나왔고 진짜 비칠 때는 55였다 → 문턱 30).

**정의할 수 없는 것을 검사하려 들지 마라.** '파묻힘'은 화소로 정의가 안 된다(늘 위에
덧그려지므로 가려지지 않는다). 검사할 수 있는 실제 위험(얼굴을 덮는가)으로 바꿔라.

**렌더 결과를 재사용하라.** 같은 그림을 루프 안에서 다시 그리다가 검사가 2분을 넘겼다.
